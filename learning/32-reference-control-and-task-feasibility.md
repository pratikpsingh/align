# A simple controller as a feasibility check

The learned actor maps observations and memory to a four-value action. When that policy times out, there are several possible reasons: the goal may be physically hard under the controller limits, the reward may teach the wrong behavior, or the actor may choose poor commands. A **reference controller** helps separate these possibilities. It directly computes a direction from the drone to its assigned target, like pointing an arrow from the current position to the destination.

For a drone at `(0, 0, 0.3)` m with a target at `(0, 0, 1.5)` m, a gain of `0.8 /s` requests `0.96 m/s` upward. The configured ceiling clips that to `0.5 m/s`; the four-value action is `(0, 0, 1, 1)`. When the drone gets close, the requested speed shrinks, allowing it to settle. The pure helpers in [the construction contract](../src/align/simulation/multi_drone_contract.py) implement this math. [The reference evaluator](../src/align/simulation/reference_evaluation.py) supplies the resulting actions to the same physical task as the learned policy and saves per-drone telemetry.

This rule sees the **exact assigned target and physical position**. The learned actor sees its bounded local observation instead. Thus the reference is a diagnostic upper-information baseline: success would show that reaching the shape is possible with this task/controller arrangement, not that a decentralized learned actor already knows how. The simple rule does not plan collision-free paths between crossing drones. If it causes a near miss or failure, the saved trajectories must identify that mechanism before calling the task infeasible.

The [lab procedure](../docs/33-reference-control.md) runs the reference in the original and extended schedules, retaining their outcomes separately. Validation has two levels. CPU tests confirm the correct world axis, bounded speed/action encoding, and read-only launcher command. A live simulator run must then confirm finite trajectories, exact row/reward/geometry audits, and actual success, timeout, or failure counts. The scientific question is whether any safe formation success occurs; the software probe can pass even when the controller does not complete the task.
