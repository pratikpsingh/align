# Why the same upward command can produce different motion

A drone controller takes a **requested velocity** and chooses four rotor commands. Physics then combines rotor thrust, gravity, contact, and any modeled aerodynamic interaction. If the request is `+0.19 m/s` in world Z, the drone can still descend when a downward force exceeds its available upward force or the controller reacts too slowly. A policy command is therefore an input, not a measured motion.

The saved learned flight gives a concrete example. Drone 2 crossed 0.25 m during takeoff, later fell to about 0.06 m, and contacted the ground while the requested vertical velocity was still positive. The contact detector now ends that unsafe episode. To learn why it fell, we need a controlled comparison rather than another training run.

[The replay code](../src/align/simulation/takeoff_replay.py) loads exactly the recorded command sequence. At each 0.01-second step it asks the same Lee controller for rotor actions, advances Isaac Sim once, and records position, vertical velocity, rotor actions/throttle/thrust, the vendor model's base-link force, and contact. The [CPU contract](../src/align/tasks/takeoff_replay.py) extracts the first episode and checks every replay row. One arm keeps the four active drones. A second parks three drones far away and turns off their motors, leaving one active drone. A third keeps the original four-drone scene but sets only the vendor model's downwash force to zero.

For an illustrative 0.716 kg drone, gravity weighs about `0.716 × 9.81 ≈ 7.02 N`. If the rotors supply 7.4 N upward but a modeled neighbor force adds 0.8 N downward, the net vertical force before other effects is roughly `7.4 − 7.02 − 0.8 = −0.42 N`. The drone will accelerate downward despite an upward velocity request. These numbers are a worked example, **not the measured replay values below**. The raw diagnostic records the actual simulated thrust and model force so we can check this idea.

The first test is whether the unchanged four-drone replay reproduces the saved fall. If it does not, differences in simulator layout, timing, or reset state make the intervention difficult to interpret. If it does, and both other arms avoid contact, the vendor downwash term is implicated in this specific simulated fall. If all arms fall, controller or command behavior remains a stronger candidate. Even a convincing simulator intervention does not prove the same aerodynamic cause on real hardware.

The [operational note](../docs/44-takeoff-controller-replay.md) gives the lab command and explains the reports. CPU tests cover trace extraction, row completeness, exact command parity, and the inference gate. The Isaac Sim comparison has passed; this implementation does not change the task controller, reward, actor, or training checkpoints.

The lab comparison now gives actual numbers. The original four-drone replay matched the saved contact step and its first 750 altitude values differed by only about `0.000054 m` root mean square. Near the fall, the model added almost `−3 N` vertical force to drone 2 while the controller increased rotor thrust. Removing only that model force, with four drones still in the original scene and exactly the same commands, let drone 2 climb to `1.233 m` by the end of the replay. Parking the other three drones far away gave the same contact-free result. See the [raw report](../runs/takeoff-replay/20260919T011921.157537IST-01376539/report.json) and [plot](../runs/takeoff-replay/20260919T011921.157537IST-01376539/altitude-and-force.svg).

This explains the apparent contradiction: the actor did request upward motion, and the Lee controller increased thrust, but the simulator's modeled neighbor force overcame that effort. The next task is to keep drones out of that region using a declared, bounded local safety rule or safer planned paths. Disabling aerodynamic interaction would hide the failure rather than solve it. The evidence remains specific to one saved command sequence, one pinned simulator model, and one selected drone.
