# What changes when the actor sees its own guarded flight?

In command replay, drone 2 follows a saved sequence of actor requests. If a guard redirects it at one instant, later saved requests still assume the old position. In closed-loop evaluation, its next camera-free local observation reflects the redirected flight. The LSTM receives that new observation and may issue a different next request. That feedback is why the accepted open-loop result does not predict the entire frozen-policy flight.

The data flow for each physics control step is: local observation → shared actor and LSTM → requested world-frame velocity → takeoff wake guard → Lee controller → rotor actions → new drone positions → next observation. The actor is frozen, meaning its weights do not change; its LSTM memory still evolves and resets between episodes. The centralized critic is loaded only to verify checkpoint recovery and is not used to command the drone.

For example, an actor might ask drone 2 for `(+0.10, 0, +0.14) m/s`. If a neighbor is above and to the right, the guard may replace the horizontal component with a leftward command while preserving `+0.14 m/s` vertically. At the next step the actor sees a changed target-relative vector. The saved telemetry records both requests, the applied command, rotor saturation, measured position, target, reward, and contact force. The host independently runs the same guard rule on the saved pre-step positions and requests; a changed or missing command fails the audit.

To make a fair paired comparison, replay the same checkpoint twice in the same simulator image, using identical seed, episode schedule, task, and config. The only intended change is the guard flag. Compare ground contact, closest pair distance, how long the drones reach the formation phase, formation errors, and task outcomes. Fewer contacts with no formation progress would be a useful safety observation but would not establish the paper's formation-learning claim.

The current rule needs nearby drones' requested commands as well as their relative positions. The simulator supplies those requests synchronously for this diagnostic. It has **not** demonstrated a radio protocol or delayed-message robustness. It also targets drone 2 by ID and uses hand-set 0.9 m lateral wake radius, 0.8 s prediction, and 0.55 m predicted separation margin. The [operational guide](../docs/46-frozen-policy-wake-guard.md) lists the command and artifact contract; [the source](../src/align/tasks/wake_guard.py) contains the pure selection rule. CPU checks validate the telemetry and pairing; the paired physical result is recorded below.


The paired [physical comparison](../runs/policy-guard-comparison/20260919T015609.579036IST-5a799800/report.json) illustrates why both safety and task progress matter. Across four worlds and two contact-terminated episodes per world, the unguarded actor had eight post-ascent contacts before it reached formation. The takeoff guard intervened 523 times with no unresolved choice, allowed 1,102 formation environment steps, and had four later contacts during formation. It reached farther into the task but still completed zero episodes. These are four very similar cloned worlds using one policy seed, not four independent training seeds.

For one drone in world 0, the actor requested upward velocity on about 63% of formation steps, yet its mean measured vertical velocity was downward. That observation alone cannot tell us whether downwash, controller response, or another effect dominated. The raw policy telemetry lacks a per-step vendor downwash-force field. A matched physics replay of this later segment is the next way to separate those causes. Applying the same geometric guard during formation would have triggered in only nine of the 1,102 saved formation environment steps, so simply broadening its phase switch has little support from this trace.
