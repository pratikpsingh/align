# Steering out of a modeled rotor wake

The previous experiment showed drone 2 fell when a neighbor flew above and close to it. In the pinned simulator, that geometry created a growing downward downwash force even though the controller requested more rotor thrust. A useful intervention should change the *flight geometry* while keeping the force model active.

The local wake guard looks at nearby relative positions. Suppose drone A is at `(0.5, 0.0, 0.7) m` and drone B is at `(1.2, 0.0, 0.95) m`. B is `0.25 m` higher and `0.7 m` away horizontally: A is in the declared risk region (`0.1–1.5 m` higher, within `0.9 m` horizontal). The guard can direct A sideways while preserving its requested upward velocity. It checks eight compass directions, predicts where A and local neighbors would be after `0.8 s` if their current commands stayed constant, rejects directions whose predicted pair distance is below `0.55 m`, and chooses the direction that gives the largest horizontal clearance from B. It scales horizontal speed so the full 3-D command remains within `0.5 m/s`.

This is a **velocity command intervention** between actor and Lee controller. It does not use the centralized critic or a global map. It needs nearby relative positions **and neighboring requested velocities** within the source actor's 1.5 m radius; the current replay directly reads both from the simulator. It does not establish that a deployed drone can sense positions or receive commands with the required accuracy or latency. A constant-velocity prediction is a quick screen, not collision avoidance proof.

The [pure function](../src/align/tasks/wake_guard.py) makes the rule testable without Isaac Sim. The [replay recorder](../src/align/simulation/takeoff_replay.py) saves the original request and modified command separately. The host [audit](../src/align/tasks/takeoff_replay.py) recomputes the chosen command from the saved pre-step positions and rejects a mismatched CSV. The [run guide](../docs/45-local-wake-clearance.md) explains the one-arm lab command and acceptance metrics.

The first physical test replays the existing commands for the other three drones. This isolates the geometry intervention, but it is not yet a true frozen-policy evaluation: a live actor would see the changed positions, update its LSTM state, and issue different later commands. That closed-loop check follows only if the candidate avoids contact and maintains separation in the open-loop probe.

The first physical replay supports the geometry idea in a narrow way. The guard changed 82 of the 1,017 saved takeoff commands, the drone did not contact the ground, and the closest pair stayed `0.717 m` apart. Its downward modeled force nearly disappeared even though the force model remained on. The original four-drone command replay had accumulated about `3.02 N` of modeled downward force and hit the ground. The [independent analysis](../runs/takeoff-replay-analysis/20260919T013845.620755IST-45631a55/report.json) checked each altered command and the raw safety measurements.

A host-report lookup error initially labeled the run `failed` after the simulator had completed. We kept that report and used a separate CPU analysis run to validate its unchanged raw trajectory. This is why the simulator result, data integrity, and flight outcome are separate questions.

The flight used a provisional 2.0 m scoring radius, but the actor's contract is 1.5 m. Recomputing all saved choices with a 1.5 m radius gave exactly the same commands for this trajectory. That supports interpreting this one flight under the corrected local radius; it does not claim the two radii are equivalent in other scenes. A live frozen actor still needs a separate test because its future commands would respond to the guarded motion.
