# What it means to export a recurrent actor

A training checkpoint is a large workbench: it holds the shared actor, the centralized critic, both optimizers, normalization statistics, random-number states, and progress counters. A drone making one decision needs a much smaller set: its **local observation**, actor weights, and LSTM memory. The inner velocity controller then converts the chosen velocity into rotor actions. Exporting the actor separates these jobs without claiming that the drone hardware can run the result yet.

For the current four-drone task, one actor input has 55 numbers: three normalized own velocities, three normalized target-relative coordinates, seven nearest-neighbor slots of six normalized relative coordinates/velocities, and seven slot-validity masks. Missing neighbors are padded. This matters when evaluating fewer drones: the network's input size stays 55. The actor's hidden and cell tensors each have shape `[layers, batch, hidden]`; carrying both across steps gives it temporal memory. At a new episode both are zeroed, or a zero memory mask resets them before the new observation is processed.

The output has four bounded values. Consider `[0, 0, 0.8, -0.4]` with a 0.5 m/s configured limit: the direction is up, and the commanded speed is `abs(-0.4) × 0.5 = 0.2 m/s`. The negative fourth coordinate does **not** mean down. This is the actual task decoder and is an important limitation when interpreting learned actions. A deterministic action is produced by tanh-transforming the Gaussian mean; sampled actions use the same bounded transform.

The export flow first checks the checkpoint's exact bytes against its manifest. It then reads the full training checkpoint and writes only the actor state dictionary plus observation/action configuration. A separate process sees only these exported files, reloads a new actor, and must produce byte-identical action and LSTM memory for the fixed probe observation. It also tests that episode reset clears old memory. This check establishes that the actor can run without the training critic; it does not establish correct flight.

Size and timing need separate labels. Parameter count tells us how many trainable numbers exist, but the `.pt` artifact has headers and buffers. Batch-1 CPU latency measures the Python/PyTorch call on this lab host, with warmup; it excludes sensing, communication, and the inner controller. The exporter's peak RSS includes the full learner checkpoint, so a second-process RSS measurement gives a more relevant whole-process actor footprint. Neither is an onboard RAM or deadline result. A real deployment claim requires a target board, its runtime, precision/compression choice, and measured closed-loop timing and flight quality.
