# Why a formation deadline matters

A trained actor can emit reasonable-looking commands while the task makes success unreachable on its schedule. The accepted trace showed drones about 1.2–1.3 m below the formation altitude when the shape target became active. With only 50 steps before the latest start of a 200-step success dwell, their 0.5 m/s velocity-command ceiling allowed 0.25 m of commanded travel. That calculation is a **kinematic command budget**: `remaining steps × seconds per step × maximum commanded speed`. It does not bound every possible physical overshoot, but it shows what the intended controller interface could ask for.

The next question is whether extra time changes the same policy's flight. [The timing comparison](../docs/32-frozen-policy-timing.md) holds the actor checkpoint fixed and runs two deterministic evaluations in the same image. The original arm lasts 800 steps. The extended arm gives 15 s for takeoff and 8 s for formation, preserving the 2-second dwell and other task thresholds. The simulator loads the **original source config and checkpoint hash**, then applies a separately saved timing override to the evaluation environment. It never resumes PPO training.

A small example: if a drone reaches only 0.3 m altitude after 5 seconds and commands upward at 0.1 m/s, another 10 seconds might add about 1 m if tracking remains similar. The policy could instead change its commands as its observations change; the experiment measures that rather than assuming it. We inspect target error, commanded and realized speed, pairwise spacing, and success together. A lower error with a new collision would not be a satisfactory formation improvement.

The two-arm design changes takeoff and formation duration together, so it answers whether the **combined longer schedule** helps. It cannot identify which interval matters. If it helps, a later one-factor-at-a-time comparison can isolate the cause. If it does not, inspect whether commands still point away from targets, whether the controller tracks them, and whether the reward weights teach enough progress. The source training run is immutable and the new outputs are ignored by Git, so preserve both when sharing the result.

## Result from the frozen actor

The [accepted two-arm run](../docs/32-frozen-policy-timing.md#accepted-lab-comparison) used one checkpoint and one image. Before timing differed, all 8,800 per-drone rows were identical. Extra takeoff time raised average formation-entry height from 0.237 m to 0.631 m, so the intervention changed actual flight. Yet formation error increased from 1.582 m to 1.779 m, pairwise error increased, minimum separation decreased, and every evaluation still timed out. During formation the extended actor commanded only about 0.041 m/s, less than half its baseline average, and just 34% of commands pointed toward the assigned target.

This changes how to read the earlier reachability bound. The short baseline schedule was a real command-budget problem at its observed switch state. Giving this trained actor more time removed that particular budget constraint, but did **not** make the actor solve the task. A longer schedule is therefore not a sufficient fix for this checkpoint. It may put the actor in states it rarely saw during training, so we cannot infer what a newly trained policy would do. The next simple experiment is a target-directed controller that obeys the same 0.5 m/s action interface and uses the same inner drone controller. If that controller succeeds safely, training/action selection is the main open issue. If it fails, inspect task timing, target geometry, and inner control before changing PPO.
